astro-blog-admin에는 조금 특이한 배포 방식이 있습니다. 저장소 하나, 브랜치 하나를 Cloudflare Pages와 Tencent EdgeOne Pages 두 플랫폼에 동시에 배포해, 양쪽의 기능이 대등하고 인터페이스가 동일합니다. 이 글에서는 내장 이미지 호스팅이 두 플랫폼에 어떻게 자리 잡았는지, 그리고 이중 플랫폼이 개발에 주는 이점과 교훈을 다룹니다.

## 이미지 호스팅: 올리고, 링크 받고, 그게 다

### 공개 업로드 페이지

사이트의 루트 경로는 로그인 없는 공개 업로드 페이지입니다. 이미지를 고르고, 올리고, 링크를 받는다——그뿐입니다. 관리를 보거나 설정을 만질 수는 없습니다. 관리 화면 안의 이미지 페이지에는 관리 기능이 더해집니다. 큰 미리보기, 체크박스 일괄 삭제, 라이트박스로 원본 크기 보기. 업로드할 때 PNG/JPG는 공간 절약을 위해 브라우저에서 먼저 WebP로 변환되고, 업로드 진행 상황은 페이지 위쪽의 가는 진행 바 여러 개로 표시되며 끝나면 자동으로 사라집니다.

### 링크 규칙

이미지 주소는 루트 상대 경로만 씁니다. `/<접두사>/<파일 이름>`, 도메인은 붙지 않습니다. 접두사는 설정에서 바꿀 수 있고 어떤 도메인으로 열든 상관없습니다——도메인이나 플랫폼을 바꿔도 글에 이미 적어 둔 이미지 주소는 그대로 동작합니다. 같은 이름의 파일을 다시 올리면 덮어쓰지 않고 자동으로 번호를 붙여 이름을 바꿉니다.

## 이중 스토리지: 인터페이스 하나, 백엔드 둘

### 스토리지 추상화 계층

업로드, 읽기, 목록, 삭제는 모두 통일된 스토리지 계층을 거치며 설정에 따라 분기됩니다. Cloudflare 쪽에서는 바인딩된 R2 버킷을 우선 쓰고, 없으면 S3 호환 인터페이스를 쓰고, EdgeOne 쪽에서는 플랫폼 자체의 Blob 스토리지를 씁니다. 설정 페이지의 두 번째 스토리지 이름까지 플랫폼을 따릅니다. Cloudflare에서는 "Cloudflare R2", EdgeOne에서는 "EdgeOne Blob"로 표시되지만 저장되는 설정 값은 같고, 양쪽은 서로 영향을 주지 않습니다.

### 전환해도 마이그레이션은 없다

두 스토리지는 독립적입니다. R2에 올린 이미지는 Blob으로 전환하면 보이지 않고, 되돌리면 다시 보입니다. 이 "자동으로 이사하지 않는" 설계는 의도적입니다——스토리지는 플랫폼의 자산이고, 코드의 일은 지금 돌아가고 있는 플랫폼에서 일을 제대로 처리하는 것이기 때문입니다.

## 이중 플랫폼 배포

### 빌드 시점의 플랫폼 판별

빌드 명령은 양쪽이 같습니다. 코드는 빌드 시점에 플랫폼이 주입하는 표식 변수로 "자기가 어디에 있는지"를 판별해 그 결과를 결과물에 새기고, 실행 시에는 플랫폼별 스토리지와 설정 읽기 경로를 탑니다. 코드베이스 하나, 브랜치 하나, 배포 두 번. 비슷한 저장소 두 개를 유지할 필요가 없습니다.

### 교훈: 변수 먼저, 코드는 나중

이중 플랫폼의 가장 큰 함정은 코드가 아니라 설정에 있습니다. 환경 변수와 관련된 변경은 반드시 플랫폼 쪽에서 변수를 먼저 바꾸고 되읽어 검증한 다음 코드를 푸시해야 합니다——푸시가 곧 배포라, 순서가 반대면 운영 환경이 한동안 변수가 부족한 채로 돌게 되기 때문입니다. 각 플랫폼의 변수는 독립적이라 이 규율을 두 번 실행해야 합니다.

여섯 편의 시리즈는 여기까지입니다. 블로그 본체, 다국어, 콘텐츠의 형태, 관리 화면 개요, 시각적 편집, 이미지 호스팅과 배포. 두 프로젝트 모두 오픈소스이니, GitHub 저장소에서 지금의 모습을 구경해 보세요.
